# Объединённая версия

Интерфейс подключён: запуск и ограничения описаны в [INTEGRATION.md](INTEGRATION.md). Ниже — исходная документация бэкенда; утверждение об отсутствии веб-API теперь устарело.

# ДомРадар — backend

Backend-сервис проекта «ДомРадар» (хакатон «Умный город», Минобрнауки России ×
платформа MAX). Житель пишет боту о проблеме в доме — бот классифицирует её и
проверяет, не жаловался ли уже кто-то из соседей на то же самое. Уверенное
совпадение присоединяется к существующему инциденту, а сомнительное бот просит
подтвердить явно. При
смене статуса инцидента все подписавшиеся жители получают push-уведомление.

**В чём польза для жителя, а не только для УК** — это то, ради чего вообще
стоит писать боту, а не в общий чат дома или на бумажке у подъезда:

- **Видно, что ты не один.** Ответ бота прямо говорит: "такую же проблему
  уже отметили N соседей" — это не просто вежливость, а суть продукта:
  10 разрозненных жалоб превращаются в 1 приоритетный инцидент, который
  сложнее проигнорировать, чем одну жалобу от одного человека.
- **Можно спросить "что с моей заявкой" в любой момент** (`/webhook/status-query`),
  не дожидаясь push-уведомления — жителю не нужно помнить номер заявки или
  звонить в УК, чтобы узнать статус.
- **Опасные ситуации не тонут в общей очереди.** Если человек застрял в
  лифте или пахнет газом, бот сразу советует звонить 112/в аварийную службу
  — и параллельно, в фоне, немедленно уведомляет УК, не дожидаясь суток по
  обычному SLA (см. «Категории проблем» ниже).
- **Понятные, а не технические формулировки.** Житель и УК видят "лифт не
  работает", а не внутренний слаг `elevator_out_of_service` — весь текст,
  который видят люди, генерируется через `category_label()`/`status_label()`,
  а не собирается из сырых значений enum'ов.

## Быстрый запуск (для защиты перед жюри)

```bash
cp .env.example .env      # один раз, при желании поменять значения
docker compose up -d --build
```

Через несколько секунд backend доступен на `http://localhost:8000` (порт
настраивается через `BACKEND_PORT` в `.env`). Проверка:

```bash
curl http://localhost:8000/health
```

Миграции БД применяются автоматически при старте контейнера backend
(см. `entrypoint.sh`) — никаких ручных шагов после `docker compose up` не
требуется. Полная сборка с нуля (`docker compose build --no-cache && docker
compose up -d`) укладывается в 5 минут.

Остановить и полностью очистить (включая данные в БД):

```bash
docker compose down -v
```

## Архитектура

```
MAX-бот (Участник 2)  --webhook-->  backend (этот сервис)  <-->  PostgreSQL
                                          |
                                          |-- classify() / find_or_create_incident()
                                          |   (Участник 1, вызывается in-process)
                                          |
                                          |-- MAX Bot API (push-уведомления,
                                          |   таймауты + ретраи с backoff)
                                          |
                                          '-- APScheduler: SLA-таймер (раз в
                                              N минут проверяет "зависшие"
                                              инциденты и напоминает УК)
```

Ключевое архитектурное решение: **отдельного REST API для панели УК нет**
(это осознанно опционально по ТЗ хакатона). УК взаимодействует с системой
тоже через MAX-бота — смена статуса инцидента приходит на
`POST /webhook/status-update`, так же как события от жителей. Это упрощает
систему до одного входного контракта (webhook) и одного процесса, что прямо
влияет на критерий «Стабильность».

### Модель данных (`app/models/`, миграция `alembic/versions/0001_*.py`)

- **Building** — дом (адрес, внешний ID УК).
- **User** — житель/сотрудник УК (`max_user_id`, дом, подъезд, роль).
- **Incident** — инцидент: дом, категория, объединённый текст жалоб, статус
  (`new` / `in_progress` / `resolved`), таймстемпы для SLA.
- **Report** — конкретная заявка конкретного жителя, привязанная к инциденту.
- **StatusUpdate** — лог истории смены статусов (для SLA и метрик).

Составной индекс `ix_incidents_building_category_status` на
`(building_id, category, status)` — основной путь запроса при поиске
кандидатов на дедупликацию.

### Точка интеграции с классификатором (Участник 1)

`app/services/classifier.py` — временная заглушка с согласованным
интерфейсом:

```python
classify(text: str) -> str
find_or_create_incident(building_id: int, category: str, text: str, *, db=None) -> tuple[int, bool]
```

Участник 1 подставляет свою реализацию с той же сигнатурой — вызывающий код
(`app/api/webhook.py`) менять не нужно. Подробности и причины текущего
дизайна (почему дедупликация идёт по категории, а не по fuzzy-схожести
текста) — в докстринге модуля.

### Webhook-эндпоинты (от MAX-бота, Участник 2)

Все под префиксом `/webhook`, защищены общим секретом (заголовок
`X-Webhook-Secret`, значение — `WEBHOOK_SHARED_SECRET`):

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/webhook/message` | новое текстовое сообщение жителя |
| POST | `/webhook/photo` | прикреплённое фото (скачивается по URL и сохраняется) |
| POST | `/webhook/address-confirmation` | подтверждение адреса/подъезда |
| POST | `/webhook/incident-join-confirmation` | явное подтверждение/отказ от сомнительного совпадения |
| POST | `/webhook/status-query` | житель сам спрашивает статус своих заявок (read-only, ничего не меняет) |
| POST | `/webhook/status-update` | смена статуса инцидента сотрудником УК |

Ответ на каждый запрос — единый формат `BotReplyResponse` с полем
`reply_text`, достаточным для продолжения диалога ботом, плюс структурные
поля (`incident_id`, `report_id`, `is_new_incident`, `category`, `is_urgent`,
`needs_clarification`) для бота, если он захочет обработать их отдельно от
текста (например, показать красный баннер при `is_urgent: true`).

### Категории проблем и их человекочитаемые названия (`app/services/classifier.py`)

| Категория (внутренний слаг) | Что видит человек | Срочность |
|---|---|---|
| `elevator_stuck_person` | человек застрял в лифте | 🆘 срочно |
| `gas_leak` | запах газа | 🆘 срочно |
| `elevator_noise` | лифт шумит | обычная |
| `elevator_out_of_service` | лифт не работает | обычная |
| `heating` | проблемы с отоплением | обычная |
| `water_leak` | потоп/протечка | обычная |
| `no_water` | нет воды | обычная |
| `sewage` | засор канализации | обычная |
| `common_area_lighting` | не горит свет в подъезде | обычная |
| `electricity` | нет электричества | обычная |
| `intercom` | домофон не работает | обычная |
| `roof_leak` | течёт крыша | обычная |
| `garbage` | проблемы с вывозом мусора | обычная |
| `pests` | тараканы/грызуны | обычная |
| `parking_barrier` | не работает шлагбаум | обычная |
| `playground` | повреждена детская площадка | обычная |
| `entrance_cleanliness` | грязно в подъезде | обычная |
| `other` | другое (не распознано) | обычная |

Для **срочных** категорий (`is_urgent(category)` в `classifier.py`) бот сразу
получает `is_urgent: true`, а `reply_text` дополняется советом звонить 112 —
и backend в фоне немедленно уведомляет УК этого дома
(`notify_urgent_incident`), не дожидаясь смены статуса или суточного
SLA-таймера. Это касается и дедупликации: даже если инцидент такой
категории уже открыт, каждый житель всё равно увидит совет звонить в
экстренные службы — решение позвонить не должно зависеть от того, первый
он пожаловался или пятый.

### SLA и уведомления

- При смене статуса (`/webhook/status-update`) всем подписчикам (все
  пользователи с `Report` на этот `incident_id`) в фоне (`BackgroundTasks`)
  рассылается уведомление через MAX Bot API.
- Для **срочных** категорий (см. выше) УК уведомляется немедленно при
  создании инцидента, а не только при смене статуса.
- `app/scheduler.py` каждые `SLA_CHECK_INTERVAL_MINUTES` запускает проверку:
  если открытый инцидент не менял статус дольше `SLA_THRESHOLD_HOURS` —
  автонапоминание сотрудникам УК этого дома (`role=management`).
- Все тексты уведомлений используют `category_label()`/`status_label()`
  (`app/services/classifier.py`, `app/services/labels.py`) — ни житель, ни
  УК никогда не видят сырые технические значения вроде `elevator_out_of_service`
  или `in_progress`.

### Надёжность

- Все исходящие вызовы к MAX API — с таймаутом и ограниченным числом
  ретраев с экспоненциальным backoff (`app/services/max_client.py`).
- Ошибка классификатора/дедупликации, недоступность внешнего URL с фото и
  любая необработанная ошибка перехватываются на уровне обработчика —
  сервис не падает, в лог пишется трассировка, боту возвращается осмысленный
  ответ (`ok: false` + `reply_text`), а не голый 500.
- Поля webhook и веб-формы имеют ограничения длины и очищаются от управляющих
  символов. Тело HTTP-запроса ограничено до разбора JSON.
- Поиск/создание инцидента и смена статуса выполняются в критической секции:
  внутри процесса используется `RLock`, а в PostgreSQL — advisory-блокировка.
- Повтор одинакового сообщения в заданном окне не создаёт вторую заявку.
- В production webhook закрыт при отсутствующем, шаблонном или слишком коротком
  `WEBHOOK_SHARED_SECRET`; локальный запуск без секрета разрешён только в
  `local`/`test`/`development`.
- Загрузка фото защищена от обращения к локальной сети и подмены DNS:
  проверяется каждый redirect, публичный IP, допустимый хост, размер и сигнатура
  изображения. Фото можно прикрепить только к собственной заявке.
- Сотрудник УК через webhook меняет только инциденты закреплённого дома;
  подтверждение совпадения также доступно только владельцу обращения.
- Alembic-миграции идемпотентны: повторный `docker compose up`/перезапуск
  контейнера не ломается на уже применённой схеме.

## Порты и зависимости

- **backend**: FastAPI + Uvicorn, порт `8000` (внутри контейнера), наружу —
  `BACKEND_PORT` (по умолчанию тоже `8000`).
- **db**: PostgreSQL 16, порт не публикуется наружу по умолчанию (доступен
  только внутри docker-сети `default`); healthcheck (`pg_isready`) не даёт
  backend'у стартовать раньше готовности БД.
- Стек: Python 3.11, FastAPI 0.141, SQLAlchemy 2.0 + Alembic 1.20, APScheduler
  3.11, httpx, rapidfuzz — все зависимости открытые, версии зафиксированы в
  `requirements.txt` и периодически стоит сверять с актуальными (`pip index
  versions <пакет>`), чтобы не отстать от патчей безопасности.

## Тесты

```bash
pip install -r requirements.txt pytest
pytest tests/ -v
```

Основные автотесты проверяют:

- `tests/test_dedup.py` (26 тестов) — бизнес-логика дедупликации на реальных
  формулировках жалоб (лифт/отопление/потоп/вода/электричество/домофон/крыша/
  мусор/шлагбаум и т.д.): перефразирования находят подходящего кандидата и
  при недостаточной уверенности требуют подтверждения; разные проблемы (включая разные лифтовые инциденты — авария с
  человеком внутри vs простой vs шум) — не объединяются; закрытый инцидент и
  инциденты другого дома новую заявку не подхватывают.
- `tests/test_webhook.py` (8 тестов) — тот же HTTP-слой, что дёргает бот
  (`TestClient` + FastAPI), а не только внутренние функции: онбординг через
  подтверждение адреса, явное подтверждение или отказ от объединения,
  ролевой доступ к смене статуса (403 для жителя), safety-уведомление
  для опасных категорий, самостоятельный запрос статуса, проверка секрета
  webhook.
- `tests/test_limits_and_concurrency.py` проверяет ограничения полей и тела
  запроса, одновременные обращения, повторную доставку, смену статуса и
  идемпотентность веб-формы.

Оба файла работают на SQLite in-memory (поднятый Postgres не требуется) и
**герметичны** — не зависят от того, лежит ли рядом `.env` с реальными
значениями (`WEBHOOK_SHARED_SECRET`, `MAX_BOT_TOKEN` явно обнуляются в
фикстурах `tests/test_webhook.py`, иначе тесты могли бы неожиданно упасть
или попытаться достучаться до настоящего MAX API).

## Известные ограничения / что уточнить с командой

- Локальный запуск получает события MAX через Long Polling. Для постоянного
  публичного сервера нужно настроить HTTPS Webhook на порту 443 и подписку
  `POST /subscriptions`.
- **classify()/find_or_create_incident()** — временная keyword+эвристика,
  подлежит замене на реализацию Участника 1 с тем же интерфейсом. Если
  Участник 1 меняет набор категорий — стоит заодно обновить `_CATEGORY_LABELS`
  и `_URGENT_CATEGORIES` в том же файле, иначе новые категории будут
  показываться жителям как сырой слаг (сработает безопасный fallback
  "заменить `_` на пробел", но это не так красиво) и не получат
  safety-обработку, даже если по смыслу тоже срочные.
- **"Срочные" категории — это подсказка жителю звонить в экстренные службы,
  а не система экстренного реагирования.** Backend не может гарантировать
  доставку push за секунды (сеть, недоступность MAX API и т.д.), поэтому
  reply_text всегда советует звонить 112/в аварийную службу самостоятельно,
  а не полагаться только на то, что бот кого-то уведомит.
- REST API для веб-панели УК осознанно не делается (см. «Архитектура» выше).

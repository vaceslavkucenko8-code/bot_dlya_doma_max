# ДомРадар: интерфейс и бэкенд вместе

## Запуск на компьютере

Установите зависимости из requirements.txt, скопируйте `.env.example` в `.env`, укажите `MAX_BOT_TOKEN` и запустите `python run_local.py`.
Адрес: http://127.0.0.1:3002/. Остановка — Ctrl+C. Сервер слушает только этот компьютер.
Локальная SQLite-база: `data/domradar.sqlite3`. Порт можно задать переменной LOCAL_PORT.
Тот же процесс запускает MAX-бота через Long Polling. Бот доступен по ссылке
https://max.ru/t576_hakaton_max_bot и работает, пока запущен `run_local.py`.

## Что подключено

- Рабочие экраны жителя и диспетчера отделены явным выбором роли. Макеты объявлений и контактов вынесены в отдельный раздел «Демонстрация».
- Форма, предварительная проверка, присоединение/отдельное обращение, список, история сообщений и смена статуса работают с моделями нового backend.
- Бот и веб-интерфейс используют общие таблицы Building, User, Incident, Report, StatusUpdate.
- Правила объединения используют консервативную схему V6: дом, гранулярную категорию, временное окно, локацию и текстовую похожесть. Уверенные совпадения присоединяются, сомнительные требуют явного подтверждения, конфликтующие подъезды и устаревшие случаи разделяются.
- Профиль дома сохраняется через `/api/profile` в базе, а не localStorage. Старый сохранённый адрес браузера автоматически не переносится: его нужно один раз указать в новой версии.
- После сохранения дома адрес не дублируется в форме; изменить его можно через блок «Ваш адрес».
- Защита повторной отправки — таблица web_receipts. Для PostgreSQL добавлена миграция 0002, локальный запуск создаёт таблицы автоматически.
- Статусы отображаются в прежних формулировках; сервер использует new/in_progress/resolved.
- Импорт предыдущей базы: `python import_legacy.py ПУТЬ_К_БАЗЕ`. Исходник открывается только для чтения. Повторный запуск не дублирует инциденты. Номера меняются на числовые; старые номера сохраняются в журнале StatusUpdate.

## Границы текущей версии

Это локальная объединённая версия, не готовая публичная авторизация. Веб-интерфейс использует один общий локальный профиль жителя и отдельного локального диспетчера. API веб-панели отключён вне ENVIRONMENT=local и проверяет адрес клиента, Host и Origin. Не публиковать через туннель/прокси до внедрения персональных сессий и прав сотрудников.

MAX-адаптер использует актуальный домен `platform-api2.max.ru`, токен в заголовке `Authorization` и локальный Long Polling. Токен хранится только в исключённом из проекта файле `.env`. Для публичного постоянного запуска Long Polling нужно заменить на HTTPS Webhook, как рекомендует MAX.

Госуслуги/ЕСИА не подключены. Объявления остаются демонстрационными; контакты не заполнены, поскольку соответствующих моделей нет в архиве.

## Ограничения данных и конкурентные запросы

- Сервер ограничивает длину текста, адреса, подъезда, заметок, идентификаторов и всего тела запроса.
- Создание пользователя и дома устойчиво к одновременным запросам.
- Операции поиска/создания инцидента, смены статуса и отделения обращения защищены общей критической секцией. Для PostgreSQL используется транзакционная advisory-блокировка.
- Повторная доставка одинакового сообщения не создаёт ещё одну заявку.
- Квитанция веб-формы вынесена в модель `WebReceipt` и защищает от двойной отправки между процессами.

## Защита webhook, фото и прав доступа

- В production webhook закрыт, пока не задан отдельный секрет длиной не менее 16 символов. Значения-заглушки из примера конфигурации отклоняются; секрет сравнивается безопасным способом.
- Фото можно прикрепить только к собственной заявке. Ссылка проверяется перед каждым переходом: разрешены только публичные HTTP(S)-адреса, действует список `PHOTO_ALLOWED_HOSTS`, ограничение размера и проверка реального формата изображения.
- Незнакомый идентификатор пользователя в обычном сообщении, запросе статуса или загрузке фото не создаёт скрытую запись в базе.
- Житель может подтвердить или отделить только своё обращение. Сотрудник УК через бот меняет статусы только у инцидентов закреплённого за ним дома.

## Проверка

106 тестов. Проверены дедупликация и подтверждение совпадений, ограничения входных данных, параллельные обращения, повторная доставка, двойная смена статуса, роли, защита webhook и фото, права на заявки, контракт MAX API и демонстрационный раздел интерфейса. Дополнительно выполнена живая проверка токена, профиля бота и получения обновлений через MAX API. Текущий прогон выполнен на SQLite; PostgreSQL/Docker не проверялся.

Прежняя рабочая версия остаётся в соседней папке domradar. Новая версия — domradar-integrated.
